# autable 权限模型

本文档是 autable 权限系统的唯一权威规范。所有权限相关的实现、评审、排查都以本文为准;实现与本文不一致时,以本文为目标修正实现。

## 设计原则

1. **默认拒绝(default deny)**:没有授权就没有权限。任何"未被权限覆盖所以放行"的行为都是漏洞。
2. **服务端是唯一边界**:前端的一切过滤只是体验优化。任何用户直接调用任何 API 的组合,都不能看到或改到授权之外的数据。
3. **数据与结构分离**:作用于**数据**(cell 值、行、文件)的权限可以授权给任何主体;作用于**代码与结构**(应用、工作流、公式、schema、视图、权限)的写操作只属于管理员,不可授权。两者互不隐含:数据授权再多也不能改结构。
4. **权限的边界只能由管理员定义**:能改变"别人能看到什么、能做什么"的操作(视图定义、公式、授权、角色、工作流、应用)全部管理员独占。可授权出去的只有"在既定边界内做事"的能力:读写数据、打开应用、运行工作流。
5. **管理员是部署关口**:autable 中的代码和结构只由管理员写入。其他开发者在 autable 之外编写代码(应用、工作流脚本),由管理员账号部署到 autable;评审发生在 autable 之外。autable 不提供"提交—审批"的中间状态,也没有其他权限模式。

## 主体(Subject)

| 主体 | 标识 | 说明 |
|---|---|---|
| 用户 | user id | 登录用户 |
| 角色 | `role:<db>:<name>` | 一组授权的集合;成员(用户或 workflow)继承角色的全部授权,取并集 |
| workflow | `workflow:<id>` | workflow 代码中的 `tables` / `users` / `files` 以此身份执行,数据授权由管理员配置 |

有效权限 = 直接授权 ∪ 所属各角色的授权,同一权限取最高档。

**管理员不是可授权的主体**:管理员由配置文件 `auth.admins` 给出,不能被授予、不能通过任何 API 设置;workflow 主体和角色永远不是管理员。管理员绕过一切数据检查,见[管理员](#管理员)。

## 数据层权限

### 字段位权限(读 / 改 / 增)

每个字段三个**互相独立**的开关,存储为位掩码:

| 位 | 含义 | 生效时机 |
|---|---|---|
| 读 read | 返回的行里包含该字段的值 | 一切读取路径(列表、查询、写操作的响应体、历史) |
| 改 update | 允许修改已存在行的该字段 | `UpdateRow` / upsert 命中已有行 |
| 增 create | 允许在新建行时填写该字段 | `CreateRow` / upsert 新建行 |

- 三者独立:可以配"只能建时填、之后不能改"(一次性字段),也可以配"能改但读不回显"。
- 无读权限的字段:值在所有响应体中**一律剔除**——包括创建/修改/删除操作自己的响应体。字段的存在(名字、类型)不保密,值保密。
- 写请求中出现无权字段 → 整个请求 403 拒绝(不做静默丢弃)。
- 兼容:历史授权 Level `1` 解释为 `读`,`2` 解释为 `读|改|增`。
- `field_set` 授权是对整表所有字段的批量位授权,与单字段授权取并集。

### 行级权限:视图 = 行集边界

**视图是 record 层权限的唯一边界。** 一个主体能接触到的行(行集)= 其拥有**视图读**授权的所有视图所筛选行的**并集**。

- **"all" 是一个真实的内置视图**(无过滤条件,即全表),和其他视图一样需要授权才能读。API 中视图名为空一律按 `all` 解释——不存在"不带视图 = 无限制"的路径。
- 读取必须指定一个已授权的视图;请求级的 query / search / sort 只能在视图结果上 **AND 收窄**,永远不能放宽。
- 视图查询支持 **`$current_user` 动态变量**,解析时替换为**当前用户的 email**。一个 `提交人 = $current_user` 的视图即可实现按人隔离,不需要每人建一个视图。非用户主体(workflow、角色本身)没有 email,`$current_user` 对它们解析为其主体标识,通常不会命中任何行——给 workflow 授权时应选择不含 `$current_user` 的视图。
- **视图的新建、修改、删除管理员独占**。视图定义就是行级权限的定义,能改视图 = 能改权限边界。`view_set` / `view` 授权只表达"可以读哪些视图"。

### 写入规则

| 操作 | 行级校验 | 其他要求 |
|---|---|---|
| 新建行 | **无**(行还不存在,校验无意义) | `record.create` + 所填字段的`增`位 |
| 修改行 | **必须**:目标行 ∈ 行集,否则 404 | 所改字段的`改`位 |
| 删除行 | **必须**:目标行 ∈ 行集,否则 404 | `record.delete` |
| upsert | match 查询**限定在行集内**;命中→按修改处理,未命中→按新建处理 | 对应上两行 |

- 新建永远明确返回成功/失败(提交数据的用户必须得到确定的结果),即使新建出的行落在自己行集之外、随后自己看不见。
- **凡是触碰已存在行的操作,一律行级校验**。行不在行集内时返回 404(按不存在处理),不返回 403——不泄露行的存在性。
- `record.create` / `record.delete` 是表级的行操作开关,与字段位权限相互独立、同时校验。

### 文件

- 文件上传后处于未绑定状态,**任何人不可见**;由上传者本人一次性绑定到某行(不可移动到其他表/行)。
- 文件的下载与元数据读取是**行级**的:文件所绑定的行必须在访问者的行集内,且访问者拥有该表的 `file` 授权。表级 file 授权不再单独构成可见性。

### 关联字段(relation)

- 关联字段存储的只是目标表的 record id,本身不泄露数据。
- 关联标签(id → 显示文本)的解析受目标表行集约束:目标行不在访问者行集内时只显示 `#id`。需要展示标签时,由管理员给目标表授一个合适的只读视图。

## 管理员

### 身份

- 管理员在配置文件中列出,每项必须是 email:

  ```yaml
  auth:
    admins:
      - "admin@example.com"
    password:
      enabled: true
  ```

- 判定方式:配置项去掉首尾空白后,与当前登录用户的 email **不区分大小写**比较。workflow 主体(`workflow:<id>`)与角色永远不是管理员。
- 没有任何 API 能设置或撤销管理员;改变管理员只能改配置文件。
- `auth.admins` 为空时服务照常启动,但会记录一条警告;此时**没有任何人能管理任何东西**(建库、改 schema、授权、工作流、应用都无人可做)。

### 能力

管理员可以对**所有数据库**做一切操作,绕过一切数据层检查(字段位、视图行集、record、file)。不存在数据库 owner 的概念:没有 owner 表,也没有 owner 检查。

**管理员独占清单**(不可授权,非管理员一律 403):

- 创建数据库。
- 表的创建与删除。
- 字段的一切变更:新增、修改、删除、移动位置,以及公式字段的一切(新建公式字段、修改公式体、把字段改成公式)。公式在服务端以**全行数据**(含定义者之外任何人不可读的字段)求值,是唯一能横穿字段读权限的机制,因此只能由本就看得到一切的管理员定义。新增字段对非管理员的唯一例外是"什么都不改变"的幂等请求,见 [API 行为规范](#api-行为规范)。
- 视图的新建、修改、删除。
- 授权(grants)与角色(roles)的一切管理,包括列出角色。
- runner 列表与 runner token(`GET` / `POST /api/databases/{db}/runners`)。
- 工作流:上传 / push(首次 push 即创建工作流)、发布、回滚、源码下载、删除、版本列表与详情(触发器、设置、secret 名称、vars),设置(启用/停用、超时、保留天数),设置 secrets 与 vars,运行记录的列表与完整详情(event、日志),取消运行。secret 的值任何 API 都不返回。
- 应用:上传 / push(首次 push 即创建应用)、发布、回滚、预览 `/apps/{db}/{name}/@N/`、源码下载、删除、版本列表。

## 应用与工作流

应用和工作流是管理员部署的代码。可以授权给其他主体的只有"使用"它们的能力,每个 scope 只有一档 level `1`:

| scope | resource | level 1 的含义 |
|---|---|---|
| `app_set` | 数据库名 | 打开该数据库的所有应用 |
| `app` | app id | 打开该应用 |
| `workflow` | workflow id | 运行该工作流 |

授权请求中这三个 scope 的 level > 1 → 400。不存在 `workflow_set`。

### 打开应用

- 能打开的应用出现在 `GET /api/databases/{db}/apps` 中,其已发布版本可在 `/apps/{db}/{name}/` 打开。
- `GET /api/databases/{db}/apps/{name}` 对能打开的用户可用,但非管理员得到的 `versions` 恒为空列表。
- 预览未发布版本(`/@N/`)、源码下载、版本列表都是管理员独占。
- 应用运行在用户自己的浏览器里,它发出的每一个 API 请求都以**该用户自己的权限**校验,与在 autable 界面中完全相同。应用看不到用户看不到的数据;应用中隐藏某一列不构成保护,字段权限才是。

### 运行工作流

- 有运行权的用户可以启动工作流的 **manual 触发器**:`POST /api/databases/{db}/workflows/{name}/runs`(`{trigger?, input?, wait?}`)。运行**仍以 `workflow:<id>` 为主体执行**,即使用工作流自己的授权,而不是调用者的授权。schedule、recordChanged、webhook 触发器不能由用户启动。
- `GET /api/databases/{db}/workflows` 对有运行权的用户只列出已启用、已发布且有 manual 触发器的工作流,只含 id、name、title、已发布版本与 manual 触发器(及其 `fields`);版本、设置、secrets、vars 与其他触发器不返回。
- 有运行权的用户只能读取**自己启动的**运行:`GET .../runs/{id}` 只含状态、触发器、output、error 与时间戳,不含 event 与日志;别人的运行一律 404。运行列表、取消运行只对管理员开放。
- 停用(`enabled: false`)是管理员的开关,运行权不能绕过:已停用的工作流不出现在非管理员的列表中,非管理员启动它 → 409。管理员仍可启动已停用工作流的 manual 触发器做测试。
- 授予运行权等于把工作流本身的权力委托给调用者,这是刻意的设计,见[已知的非强制边界](#已知的非强制边界)。

### 工作流触发与 webhook

- **recordChanged**:行变更交给工作流前按 `workflow:<id>` 的字段读权限过滤(值、diff、变更字段列表);该主体读不到任何字段时不触发。工作流自己的运行写入的变更默认不触发它自己(`includeOwnWrites: false`)。
- **webhook**:`/api/hooks/{db}/{name}/{path}` 不使用会话、不做 CSRF 检查,任何人都能请求;请求原样交给代码,由代码自行认证(签名、共享密钥)。已停用或未发布的工作流的 webhook 返回 404。

## API 行为规范

所有返回行数据的端点必须遵守:

1. **读取**(`GET /rows`、`POST /rows/query`、`/rows/page`、搜索):必须解析出一个已授权视图(空 = `all`),`CanReadView` 不过 → 403;结果行 ∈ 该视图,值经字段读过滤;`total` 只统计视图内的行。
2. **写入**(`POST /rows`、`PATCH /rows/{id}`、`DELETE /rows/{id}`、`/rows/upsert`):按[写入规则](#写入规则);**响应体的行值必须经过字段读过滤**。
3. **行历史**(`GET /rows/{id}/history`):对有权限的用户开放。目标行必须 ∈ 行集(否则 404,与不存在不可区分),历史值与 diff 按字段读权限过滤。
4. **文件**(`GET /files/{id}`、`POST /files/metadata`):行级校验(见上)。
5. 查询/排序/搜索中引用无读权限的字段 → 403(防侧信道);全文搜索只在可读字段上构建。
6. **workflow 的数据访问**(代码中的 `tables`、`users`、`files`)以 `workflow:<id>` 为主体走完全相同的检查,无任何捷径。workflow 主体的数据授权与用户一样由管理员配置。
7. **新增字段**(`POST /api/tables/{db}/{table}/fields`):管理员新建或恢复字段。其他任何人(包括所有 workflow 主体)的请求只有在**不会改变任何东西**时成功——所请求的字段全部已存在、未删除且类型相同——否则 403 `adding fields requires an admin`。这样幂等的"确保字段存在"脚本在管理员加好列之后可以继续运行。非管理员(包括 workflow 主体)另需对该表有任意授权。
8. **授权校验**(`POST /api/permissions/grants`,管理员独占):已移除的 scope `field_add`、`field_modify`、`workflow_set` → 400 unsupported scope;`app_set` / `app` / `workflow` 的 level > 1 → 400;`view_set` / `view` 的 level > 1 → 400(视图授权只读)。
9. **身份与目录**:`GET /api/auth/me` 以及登录、注册的响应包含 `is_admin`,仅供界面展示;服务端对每个请求独立判定。目录(`GET /api/metadata`)中数据库不带任何 permission level;表的 `permission_level` 为 2(管理员)或 1(可见);字段带位掩码(管理员为 7);视图对管理员为 2、对有读授权者为 1。
10. **注册**:`POST /api/auth/register` 遇到已注册的 email → 409(不会覆盖已有账号的密码)。
11. **跨站请求防护(CSRF)**:适用于 `/api/` 下不带 `Authorization: Bearer` 的 POST / PUT / PATCH / DELETE 请求。带 bearer 的请求(autablectl、脚本)不受限;runner WebSocket 是 GET;workflow webhook(`/api/hooks/...`,任何方法)完全豁免——不使用会话,不限 content type,由工作流代码认证请求。
    - 有 `Sec-Fetch-Site` 时,必须是 `same-origin` 或 `none`,否则 403。
    - 没有 `Sec-Fetch-Site` 而有 `Origin` 时,Origin 必须等于 `server.public_url` 的 origin,或其 host[:port] 等于请求的 Host 头,否则 403;`Origin: null` 一律拒绝。
    - JSON 端点要求 `Content-Type: application/json`(允许带 charset 参数),否则 415。
12. **会话 cookie**:`server.public_url` 为 https 时名为 `__Host-autable_session` 并带 `Secure`;纯 http(本地开发、e2e)时仍为 `autable_session`。两者都是 HttpOnly、SameSite=Lax、Path=/。

## 已知的非强制边界

以下是文档约定,不做机器强制。它们是刻意的设计取舍,授权时需要知晓:

- **公式字段是管理员定义的投影**:公式可读全行。给某人某公式字段的读权限,等于让他看到公式所表达的任何信息。管理员写公式时自行负责。
- **运行工作流 = 借用工作流的权力**:运行以 `workflow:<id>` 的授权执行,不受调用者自身授权限制;运行输出原样返回给调用者,不做字段过滤。授予某人某工作流的运行权,等于允许他让该工作流以它的授权做脚本所做的一切,并看到脚本返回的一切。管理员写工作流时自行负责。
- **workflow 运行记录含数据**:run 的 event、output 与日志会包含它处理过的行数据,且不做字段过滤。因此运行列表与完整详情只对管理员开放;启动者只看到自己运行的状态与 output。
- **webhook 是公开入口**:谁都能调用 webhook 地址,认证完全由工作流代码负责。管理员写工作流时自行负责。
- 字段名、表名、视图名等 schema 信息对有该表任意授权的用户可见,不保密。
- **管理员按 email 识别**:开放密码注册时,谁先用某个管理员 email 注册,谁就得到管理员权限。管理员应在部署该配置之前或同时注册自己的账号,或改用 OIDC(OIDC 登录会拒绝 `email_verified` 为 false 的身份;应使用会验证 email 的身份提供方)。

## 升级与迁移

**升级前先配置 `auth.admins`,否则没有人能管理任何东西。**

系统数据库迁移 6 → 7:

- 删除 `database_owner_models` 表:数据库 owner 不复存在。原 owner 不在 `auth.admins` 中时失去一切管理能力;他们原先依靠 owner 身份绕过数据检查,如果没有显式的数据授权,升级后也读不到数据,需要管理员补授权。
- 删除 scope 为 `field_add`、`field_modify`、`workflow_set`、`workflow` 的授权。旧的 `workflow` 授权表示查看/编辑工作流,而不是运行;运行权需要管理员有意识地重新授予。依赖 `field_add` 自动建列的工作流,需要管理员先加好列(之后幂等的建列请求照常成功)。
- `app` / `app_set` 授权的 level 归一为 1:原先能 push / 发布应用的用户只剩打开权。
- 数据 scope 的授权——包括 workflow 主体和角色持有的——保持不变。

其他升级影响:

- https 部署因会话 cookie 改名为 `__Host-autable_session`,升级后所有人在浏览器中需要重新登录一次;autablectl 的 bearer token 不受影响。
- 行级边界(内置 `all` 视图需授权)当初上线时采用**一刀切默认拒绝**:非管理员主体在获得视图授权前读不到任何行。按需授权视图(通常从 `view:all read` 或一个 `$current_user` 隔离视图开始);不做自动补发,换取模型从第一天起就是干净的默认拒绝。

系统数据库迁移 7 → 8(workflows v2,见 `docs/design/workflows-v2.md`):

- 删除旧的节点式工作流表;新工作流 id 从头开始。旧的运行历史(LevelDB 中的 `whistory_` 键)在服务启动时删除。
- 删除一切 `workflow:<id>` 主体持有的授权与角色成员身份(否则新工作流会继承旧工作流的授权),以及一切 `workflow` scope 的运行授权。工作流改写为项目并发布后,管理员需要重新授权。
- 仓库同步不再提交 `workflow/` 目录;已有的脚本文件原样保留。

## 当前状态

本文描述的管理员模型自系统数据库 schema 版本 7 起生效,取代此前的数据库 owner 模型及 `field_add`、`field_modify`、`workflow_set` 等可授权的结构权限。授权检查实现于 `internal/api/authorization.go`。
